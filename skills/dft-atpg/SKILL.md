# DFT 与 ATPG

可测性设计的价值在于**用算法把"不可观测的内部节点"变成可激励、可观测的**，
并用尽可能少的测试模式覆盖尽可能多的故障。

## 1. 四阶段链

```
01 综合 ──▶ 02 扫描插入 ──▶ 03 ATPG ──▶ 04 门级模式验证
```

| 阶段 | 脚本 | 产出 |
|------|------|------|
| 01 综合 | `flow/dft/01_synth.sh` | 门级网表 + JSON 结构 |
| 02 扫描插入 | `flow/dft/02_scan_insert.py` | 扫描网表、链统计、移位测试台 |
| 03 ATPG | `flow/dft/03_atpg.py` | 测试模式 + 覆盖率报告（可续跑） |
| 04 验证 | `flow/dft/04_pattern_verify.py` | 门级仿真 vs 参考机交叉比对 |

中间产物可续跑：`results/dft/` 下保留综合网表/扫描网表/模式/验证结果，
可跳过 01/02 直接从 03/04 继续。

## 2. 扫描插入的关键动作

- **mux-D scan**：把 DFF 复用为扫描单元，均衡切分多条链（本项目 4 链）；
- **观测点插入**：在高扇出内部网插入 test-only DFF 串链 —— 这是覆盖率跃升的关键；
- **复位去耦**：消除 capture 沿的复位竞争，否则模式验证会出现伪失败。

## 3. 自研 ATPG 引擎

`flow/dft/03_atpg.py` 是纯 Python 实现，三个部件：

1. **并行故障模拟 PFS**（bit-parallel）—— 用整数位运算一次模拟多个故障；
2. **PODEM 确定性生成** —— 对难测故障做回溯搜索；
3. **逐模式故障模拟取精确检测集** —— 避免"声称覆盖但实际未检测"。

**覆盖率收敛实测**：

| 配置 | 模式数 | Stuck-at 覆盖率 |
|------|-------|----------------|
| 插入观测点前 | 4,096 | 47.19% |
| 插入 48 个观测点后 | 4,096 | **100.00%**（19,814 / 19,814） |

> 用**相同模式数**对比是关键：证明覆盖率提升来自可观测性改善，而不是靠堆模式。

## 4. 门级模式验证（防自欺）

`04_pattern_verify.py` 做**双向交叉比对**：yosys 门级仿真 vs Python 图模型参考机。
本项目在此阶段抓出 4 个缺陷后达到 **64/64 PASS + mask 64/64 一致**。

> 只跑 ATPG 不看门级验证 = 没有证据。ATPG 引擎自身的 bug 必须靠独立参考模型暴露。

## 5. 规模限制（如实说明）

自研 Python ATPG 引擎在**小载体**（约 700 DFF）上可全规模跑通；
到 GPU 级网表（约 45,000 DFF，约 62 倍规模）时，纯 Python 全规模不可行 ——
因此 DFT 链在小载体上验证**方法正确性**，方法本身可迁移到大规模设计。

## 6. 量产所需的 DFT 升级项

当前实现是**入门级**（裸 4 链 + stuck-at），量产需补齐：

| 升级项 | 作用 |
|-------|------|
| EDT / 测试压缩 | 降低测试数据量与测试时间 |
| OCC（片上时钟控制） | 支持 at-speed 测试 |
| at-speed / transition delay | 覆盖时序相关缺陷 |
| MBIST | 存储器内建自测 |
| Boundary scan（JTAG） | 板级互连测试 |
| 多链 + 链均衡优化 | 压缩移位时间 |

对应商业工具：Tessent / TetraMAX。本仓库的**算法层与流程编排可复用**，引擎换商业实现即可。
